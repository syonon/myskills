# 実装計画を書く

## 概要

読みやすく、実行しやすい軽量な実装計画を書きます。重視するのは作業の構造です。何が変わるのか、どのファイルが関係するのか、各タスクは何に責任を持つのか、どのテストでその振る舞いを証明するのかを明確にする。計画は具体的に保ちつつ、逐一のコーディング手順を書き起こすような内容にはしない。DRY。YAGNI。TDD。

実装するエンジニアは十分に有能で、通常の開発コンテキストはすでに把握している前提で考える。安全に実装できるだけの方向づけは与えつつ、明らかなコーディングの仕組みまで過剰に説明しないこと。

**開始時に次を明言すること:** "writing-plans skillを使用して、実装計画を作成します。"

**保存先:** `docs/work/exec-plans/YYYYMMDD-<feature-name>.md`

## スコープ確認

仕様が複数の独立したサブシステムを含んでいる場合、それは `brainstorming` の段階でサブプロジェクト仕様に分割されているべきである。分割されていない場合は、サブシステムごとに別々の計画に分けることを提案する。各計画は、それ単体で動作しテスト可能なソフトウェアを生み出すべきである。

## ファイル構成

タスクを定義する前に、作成または変更するファイルとその責務をマッピングする。ここで分解に関する設計判断を確定させる。

- 明確な境界と明確に定義されたインターフェースを持つユニットを設計する。各ファイルには1つの明確な責務があるべきである。
- コンテキストに収まるコードについて最も的確に推論でき、ファイルが焦点を絞っているほど編集の信頼性が高まる。多くのことをやりすぎる大きなファイルよりも、小さく焦点を絞ったファイルを優先する。
- 一緒に変更されるファイルは一緒に配置する。技術レイヤーではなく、責務で分割する。
- 既存のコードベースでは、確立されたパターンに従う。コードベースが大きなファイルを使っている場合、一方的に構造を変更しない — ただし、変更対象のファイルが扱いにくいほど肥大化している場合、分割を計画に含めるのは妥当である。

この構成がタスク分解の指針となる。各タスクは、単独で意味をなす自己完結した変更を生み出すべきである。

## 細かいタスクの粒度

中規模の機能であれば、意味のあるタスクを 4〜7 個に収めることを優先します。

- タスクは、キー入力の1つひとつではなく、まとまりのある作業単位を表すべきです
- TDD はルールとして維持しつつも、ワークフローが特別に壊れやすい場合を除き、red-green-refactor の各小手順までは列挙しないでください
- 実行状況の追跡にはチェックリストを使う

## 計画ドキュメントのヘッダー

**すべての計画は、必ずこのヘッダーで始めること:**

```markdown
# [Feature Name] Implementation Plan

**Goal:** [One sentence describing what this builds]

**Architecture:** [2-3 sentences about approach]

**Tech Stack:** [Key technologies/libraries]

---
```

## タスク構造

```markdown
### Task N: [Component Name]

**Files:**

- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py`
- Test: `tests/exact/path/to/test.py`

- [ ] [タスクの目的と変更内容を簡潔に書く]
- [ ] [必要なテスト観点を書く]
- [ ] [依存する前提や注意点があれば書く]
```

デフォルトでは、完全なコードスニペットは含めないでください。
デフォルトでは、そのコマンド自体が計画上重要でない限り、正確なシェルコマンドは含めないでください。
曖昧さを避けるうえで不可欠でない限り、想定される失敗メッセージは含めないでください。

## 覚えておくこと

- ファイルパスは常に正確に書く
- 計画はデフォルトで軽量に保つ
- 完全な実装ではなく、責務とテストカバレッジを記述する
- コードスニペットは、形が自明でない場合や強く結びついている場合にのみ含める
- コマンドは、実行に実質的な助けになる場合にのみ含める
- 関連するスキルは `@` 構文で参照する
- DRY, YAGNI, TDD

## 計画レビューのループ

計画の各チャンクを作成し終えるたびに、次を行います。

1. `plan-reviewer` サブエージェントを起動する
   - 提供するもの: チャンクの内容、仕様書へのパス
2. もし ❌ Issues Found なら:
   - そのチャンクの問題を修正する
   - そのチャンクについて再度レビュー担当を起動する
   - ✅ Approved になるまで繰り返す
3. もし ✅ Approved なら: 次のチャンクへ進む（最後のチャンクなら実行引き継ぎへ進む）

**レビュー ループの指針:**

- 修正は、その計画を書いた同じエージェントが行う（コンテキストを維持するため）
- ループが 5 回を超えたら、人間に判断を仰ぐ
- レビュアーの指摘は助言であり絶対ではない。フィードバックが誤っていると考えるなら、その理由を説明する

## 実行への引き継ぎ

計画を保存したら、次を伝えます。

**"実装計画を作成しました。 `docs/work/exec-plans/active/<filename>.md`."**

## 出力スタイル

- 常に軽量フォーマットで出力する
- 最初に短い概要セクションを置く
- 役立つ場合は、領域ごとにまとめた簡潔なファイルマップを含める
- 逐次的なコーディング手順ではなく、タスク単位のチェックリストを優先する
- テストの期待値は含めるが、カバレッジ観点として要約して示す
- 最後は、完了条件を明確に書いて締める
