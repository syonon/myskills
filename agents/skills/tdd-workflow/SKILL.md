# テスト駆動開発（TDD）ワークフロー

このスキルは、すべてのコード開発が **TDD の原則**に従い、**包括的なテストカバレッジ**を備えることを保証します。

## いつ有効化するか

- 新機能や機能追加を書くとき
- バグや不具合を修正するとき
- 既存コードをリファクタリングするとき
- API エンドポイントを追加するとき
- 新しいコンポーネントを作成するとき

## TDD ワークフロー手順

- ステップ 1: テストファイルを書く（RED）
- ステップ 2: テストを実行する（失敗することを確認）
- ステップ 3: 最小限の実装を書く（GREEN）
- ステップ 4: テストを実行する（成功することを確認）
- ステップ 5: リファクタリングする（改善）
  - テストがグリーンのまま、コード品質を改善する:
  - 重複を取り除く
  - 命名を改善する
  - パフォーマンスを最適化する
  - 可読性を高める

## よくあるテストの間違い（避けるべきこと）

### ❌ NG: 実装の詳細をテストする

```typescript
// 内部状態をテストしない
expect(component.state.count).toBe(5);
```

### ✅ OK: ユーザーに見える振る舞いをテストする

```typescript
// ユーザーが目にするものをテストする
expect(screen.getByText("Count: 5")).toBeInTheDocument();
```

### ❌ NG: 壊れやすいセレクタ

```typescript
// ちょっとした変更で壊れやすい
await page.click(".css-class-xyz");
```

### ✅ OK: 意味的（セマンティック）なセレクタ

```typescript
// 変更に強い
await page.click('button:has-text("Submit")');
await page.click('[data-testid="submit-button"]');
```

### ❌ NG: テストが分離されていない

```typescript
// テスト同士が依存してしまう
test("creates user", () => {
  /* ... */
});
test("updates same user", () => {
  /* 前のテストに依存 */
});
```

### ✅ OK: 独立したテスト

```typescript
// 各テストが自分で必要なデータを用意する
test("creates user", () => {
  const user = createTestUser();
  // テストのロジック
});

test("updates user", () => {
  const user = createTestUser();
  // 更新ロジック
});
```

## ベストプラクティス

1. **まずテストを書く** - 常に TDD
2. **1テスト1アサート** - 単一の振る舞いに集中する
3. **説明的なテスト名** - 何をテストしているかが分かるようにする
4. **Arrange-Act-Assert** - 明確なテスト構造
5. **外部依存はモックする** - ユニットテストを分離する
6. **エッジケースをテストする** - null / undefined / 空 / 大きい入力など
7. **エラー経路もテストする** - 正常系だけでなく異常系も
8. **テストを高速に保つ** - ユニットテストは各 50ms 未満
9. **テスト後にクリーンアップ** - 副作用を残さない
10. **カバレッジレポートを確認** - 抜け漏れを特定する

## 必ずテストすべきエッジケース

- Null/Undefined: 入力が null の場合はどうなる？
- Empty: 配列/文字列が空の場合はどうなる？
- Invalid Types: 間違った型が渡されたらどうなる？
- Boundaries: 最小/最大値
- Errors: ネットワーク障害、DB エラー
- Race Conditions: 同時実行（並行処理）
- Large Data: 1万件以上での性能
- Special Characters: Unicode、絵文字、SQL 文字

## 成功指標（Success Metrics）

- すべてのテストが通っている（green）
- スキップまたは無効化されたテストがない
- テスト実行が高速（ユニットテストは 30 秒未満）
- E2E テストが重要なユーザーフローをカバーしている
- 本番前にテストがバグを検知できている

---

**覚えておくこと**: テストは任意ではありません。テストは、安全にリファクタリングし、迅速に開発し、本番の信頼性を担保するためのセーフティネットです。
