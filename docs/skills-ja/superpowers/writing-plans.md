# 実装計画を書く

## 概要

読みやすく、実行しやすい軽量な実装計画を書きます。重視するのは作業の構造です。何が変わるのか、どのファイルが関係するのか、各タスクは何に責任を持つのか、どのテストでその振る舞いを証明するのかを明確にします。計画は具体的に保ちつつ、逐一のコーディング手順を書き起こすような内容にはしません。DRY。YAGNI。TDD。

実装するエンジニアは十分に有能で、通常の開発コンテキストはすでに把握している前提で考えます。安全に実装できるだけの方向づけは与えつつ、明らかなコーディングの仕組みまで過剰に説明しないでください。

**開始時に次を明言すること:** "writing-plans skillを使用して、実装計画を作成します。"

**コンテキスト:** これは専用の worktree（`brainstorming` スキルが作成したもの）で実行される想定です。

**保存先:** `docs/exec-plans/YYYYMMDD-<feature-name>.md`

- （計画の保存場所に関するユーザーの希望がある場合は、こちらよりそちらを優先する）

## スコープ確認

仕様が複数の独立したサブシステムを含んでいる場合、それは `brainstorming` の段階でサブプロジェクトごとの仕様に分解されているべきです。もし分解されていないなら、サブシステムごとに計画を分けることを提案してください。各計画は、それ単体で動作し、テスト可能なソフトウェアを生み出せるものでなければなりません。

## ファイル構成

タスクを定義する前に、どのファイルを新規作成または変更するのか、それぞれが何に責任を持つのかを整理します。分解の判断はここで固まります。

- 境界が明確で、インターフェースがきちんと定義された単位として設計する。各ファイルは、明確に1つの責務を持つべきです
- 一度に把握できる範囲のコードの方が推論しやすく、焦点の定まったファイルほど編集の信頼性も高まります。多くを抱え込んだ大きなファイルより、小さく集中したファイルを優先してください
- 一緒に変更されるファイル同士は近くに置く。技術レイヤーではなく責務で分ける
- 既存コードベースでは、確立されたパターンに従う。もしそのコードベースが大きなファイルを使うスタイルであれば、一方的に再構成してはいけません。ただし、変更対象のファイルが扱いづらいほど肥大化しているなら、計画に分割を含めるのは妥当です

この構成がタスク分解の基礎になります。各タスクは、それ単体でも意味が通る自己完結した変更になるようにします。

## ひと口サイズのタスク粒度

中規模の機能であれば、意味のあるタスクを 4〜7 個に収めることを優先します。

- タスクは、キー入力の1つひとつではなく、まとまりのある作業単位を表すべきです
- TDD はルールとして維持しつつも、ワークフローが特別に壊れやすい場合を除き、red-green-refactor の各小手順までは列挙しないでください
- 実行状況の追跡にはチェックリストを使う

## 計画ドキュメントのヘッダー

**すべての計画は、必ずこのヘッダーで始めること:**

```markdown
# [Feature Name] Implementation Plan

**Goal:** [One sentence describing what this builds]

**Architecture:** [2-3 sentences about approach]

**Tech Stack:** [Key technologies/libraries]

---
```

## タスク構造

```markdown
### Task N: [Component Name]

**Files:**

- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py`
- Test: `tests/exact/path/to/test.py`

- [ ] [タスクの目的と変更内容を簡潔に書く]
- [ ] [必要なテスト観点を書く]
- [ ] [依存する前提や注意点があれば書く]
```

デフォルトでは、完全なコードスニペットは含めないでください。
デフォルトでは、そのコマンド自体が計画上重要でない限り、正確なシェルコマンドは含めないでください。
曖昧さを避けるうえで不可欠でない限り、想定される失敗メッセージは含めないでください。

## 覚えておくこと

- ファイルパスは常に正確に書く
- 計画はデフォルトで軽量に保つ
- 完全な実装ではなく、責務とテストカバレッジを記述する
- コードスニペットは、形が自明でない場合や強く結びついている場合にのみ含める
- コマンドは、実行に実質的な助けになる場合にのみ含める
- 関連するスキルは `@` 構文で参照する
- DRY, YAGNI, TDD

## 計画レビューのループ

計画の各チャンクを作成し終えるたびに、次を行います。

1. `plan-reviewer` サブエージェントを起動する
   - 提供するもの: チャンクの内容、仕様書へのパス
2. もし ❌ Issues Found なら:
   - そのチャンクの問題を修正する
   - そのチャンクについて再度レビュー担当を起動する
   - ✅ Approved になるまで繰り返す
3. もし ✅ Approved なら: 次のチャンクへ進む（最後のチャンクなら実行引き継ぎへ進む）

**チャンク境界:** `## Chunk N: <name>` という見出しでチャンクを区切ります。各チャンクは 1000 行以下で、論理的に自己完結している必要があります。

**レビュー ループの指針:**

- 修正は、その計画を書いた同じエージェントが行う（コンテキストを維持するため）
- ループが 5 回を超えたら、人間に判断を仰ぐ
- レビュアーの指摘は助言であり絶対ではない。フィードバックが誤っていると考えるなら、その理由を説明する

## 実行への引き継ぎ

計画を保存したら、次を伝えます。

**"実装計画を作成しました。 `docs/exec-plans/<filename>.md`."**

## 出力スタイル

- 常に軽量フォーマットで出力する
- 最初に短い概要セクションを置く
- 役立つ場合は、領域ごとにまとめた簡潔なファイルマップを含める
- 逐次的なコーディング手順ではなく、タスク単位のチェックリストを優先する
- テストの期待値は含めるが、カバレッジ観点として要約して示す
- 最後は、完了条件を明確に書いて締める
