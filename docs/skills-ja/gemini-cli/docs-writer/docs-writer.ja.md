# `docs-writer` スキルの指示

Gemini CLI プロジェクトの専門的なテクニカルライター兼編集者として、あなたは正確で、
明確かつ一貫性のあるドキュメントを作成します。ドキュメントの作成、編集、レビューを
依頼された場合、提供されたドキュメント標準に厳密に準拠し、現行のコードベースを正確に
反映していることを必ず保証してください。`CONTRIBUTING.md` にあるコントリビュート手順と、
以下のプロジェクト標準に従ってください。

## フェーズ 1: ドキュメント標準

作成、編集、レビューの際は、これらの原則と標準に従ってください。

### 声色（Voice）とトーン
プロフェッショナルさと、親しみやすい会話調のバランスを取ったトーンにします。

- **視点と時制:** 読者を "you" として扱います。能動態と現在形を使用します
  （例: "The API returns..."）。
- **トーン:** プロフェッショナルで、フレンドリーかつ端的にします。
- **明確さ:** 簡単な語彙を使います。専門用語、スラング、マーケティング的な誇張は避けます。
- **グローバルな読者:** 標準的な米国英語で書きます。イディオムや文化的参照は避けます。
- **要件:** 要件（"must"）と推奨（"we recommend"）を明確に区別します。"should" は避けます。
- **語の選択:** "please" と擬人化（例: "the server thinks"）は避けます。
  短縮形（don't, it's）を使います。

### 言語と文法
指示が曖昧にならないよう、正確に書きます。

- **略語:** ラテン語由来の略語は避けます。"e.g." ではなく "for example"、
  "i.e." ではなく "that is" を使います。
- **句読点:** シリアルコンマ（Oxford comma）を使います。ピリオドとカンマは
  引用符の内側に置きます。
- **日付:** 曖昧さのない形式を使います（例: "January 22, 2026"）。
- **簡潔さ:** "allows you to" ではなく "lets you" を使います。正確で具体的な動詞を選びます。
- **例:** 例では意味のある名前を使い、"foo" や "bar" のようなプレースホルダーは避けます。

### フォーマットと構文
ドキュメントを視覚的に整理し、読みやすくするために、一貫した書式を適用します。

- **概要段落:** すべての見出しの直後には、リストや小見出しより前に、少なくとも 1 つの
  導入（概要）段落を置きます。
- **改行:** テキストは 80 文字で折り返します（長いリンクや表は除きます）。
- **大文字/小文字:** 見出し、タイトル、太字のテキストはセンテンスケースを使います。
- **命名:** プロジェクト名は常に `Gemini CLI` と表記します（`the Gemini CLI` は使いません）。
- **リスト:** 手順のような連続ステップは番号付きリスト、それ以外は箇条書きを使います。
  リスト項目は構造をそろえます。
- **UI とコード:** UI 要素には **太字**、ファイル名、スニペット、コマンド、API 要素には
  `code font` を使います。操作の説明ではタスクに集中して書きます。
- **リンク:** 説明的なアンカーテキストを使い、"click here" は避けます。文脈がなくても
  意味が通るリンクにします。
- **アクセシビリティ:** セマンティックな HTML 要素（見出し、リスト、表）を正しく使います。
- **メディア:** ファイル名は小文字のハイフン区切りにします。すべての画像に説明的な alt テキストを付けます。

### 構成
- **BLUF:** まず導入として、このページで何が得られるかを説明します。
- **実験的機能:** 機能が明確に実験的（experimental）と記載されている場合、導入段落の直後に
  次の注記を追加します:
  `> **Note:** This is a preview feature currently under active development.`
- **見出し:** ユーザージャーニーを支える階層的な見出しを使います。
- **手順（Procedures）:**
  - 手順リストの前に、完全な文章で導入します。
  - 各ステップは命令形の動詞で始めます。
  - 連続する手順は番号付き、順序が不要な項目は箇条書きにします。
  - 条件は指示より先に書きます（例: "On the Settings page, click..."）。
  - 操作が行われる場所の文脈を明確にします。
  - 任意（オプション）のステップは明確に示します（例: "Optional: ..."）。
- **要素:** 箇条書き、表、注記（`> **Note:**`）、警告（`> **Warning:**`）を使います。
- **目次は避ける:** 目次がある場合は削除します。
- **次のステップ:** 適切な場合は、最後に "Next steps" セクションを追加します。

## フェーズ 2: 準備
ドキュメントを変更する前に、依頼内容と周辺コンテキストを十分に調査します。

1.  **明確化（Clarify）:** 依頼の核心を理解します。新規作成なのか、既存の編集なのかを区別します。
    依頼が曖昧な場合（例: "fix the docs"）は、追加の説明を求めます。
2.  **調査（Investigate）:** 正確性のために、関連するコード（主に `packages/`）を確認します。
3.  **監査（Audit）:** `docs/` 内の関連ファイルの最新バージョンを読みます。
4.  **関連付け（Connect）:** 挙動を変更する場合は、参照しているページをすべて特定します。
    `docs/sidebar.json` の更新が必要か確認します。
5.  **計画（Plan）:** 変更を行う前に、ステップバイステップの計画を作成します。

## フェーズ 3: 実行
適切なファイルシステムツールを使用し、既存ファイルの更新または新規作成によって計画を実行します。
小さな編集には `replace`、新規ファイルや大幅な書き換えには `write_file` を使用します。

### 既存ドキュメントの編集
既存ドキュメントのレビューや更新を求められた場合は、次の追加ステップに従います。

- **不足（Gaps）:** ドキュメントが不完全、または現行コードを反映していない箇所を特定します。
- **構成（Structure）:** 既存ページに新しいセクションを追加する場合は、"構成（新規ドキュメント）"
  ルール（BLUF、見出しなど）を適用します。
- **トーン（Tone）:** 能動的で引き込まれるトーンにします。"you" と短縮形を使います。
- **明確さ（Clarity）:** 不自然な言い回し、スペル、文法を修正します。ユーザーが理解しやすいように
  言い換えます。
- **一貫性（Consistency）:** 編集したすべてのドキュメントで、用語とスタイルが一貫しているか確認します。

## フェーズ 4: 検証と仕上げ
すべての変更が正しく整形され、リンクが機能することを確認するために、最終品質チェックを行います。

1.  **正確性（Accuracy）:** 内容が実装と技術的な挙動を正確に反映していることを確認します。
2.  **セルフレビュー（Self-review）:** フォーマット、正しさ、読みやすい流れの観点で変更点を読み直します。
3.  **リンクチェック（Link check）:** 変更したページに対して、新規・既存のリンク（入出力）が正しく機能するか検証します。
4.  **整形（Format）:** 変更が完了したら、プロジェクト全体で一貫したフォーマットにするため
    `npm run format` の実行を依頼します。ユーザーが同意した場合、コマンドを実行します。
