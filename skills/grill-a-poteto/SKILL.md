# Grill a poteto

目標は、別セッションの poteto-mode がそのまま読んで作業に移れる指示書を完成させることです。仕様の壁打ちは、指示書を埋めるために行います。作業そのもの（実装、修正、原因調査）は始めません。

pstack の `skills/poteto-help/references/prompting.md` が手元にあれば、最初に読んでください。その Put in と Leave out を判定基準にします。

## 質問のしかた

指示書の空いている項目について、ユーザーに質問を一度に一つずつ行ってください。それぞれの質問には、あなたが推奨する回答を添えてください。

分岐が現れるたびに、次のどれに当たるかを一言で宣言してください。

- **人間が決める。** 製品や好みの判断、スコープ、制約。質問します。
- **観測で決める。** 挙動、タイミング、性能、見た目など、動かせば分かること。質問せず、「未決」に積みます。
- **poteto-mode に任せる。** 実装方法、設計、手順、使うスキル。質問も推奨もしません。

完了チェックは、合格か不合格かで判定できる形になるまで詰めてください。「もっと良くする」や「1時間取り組む」はチェックではありません。

目標が複数のリリースにまたがりそうなら、目標を分けるかどうかと、その順序を人間に聞いてください。分けるなら指示書を目標ごとに作ります。PR の分け方やスタックにするかどうかは poteto-mode に任せ、質問しません。

コードベースを調べれば分かる事実（現在の挙動、設定の場所、関係する画面やコマンド）は、質問せずに調べてください。原因を探しに行ってはいけません。

ユーザーが原因の推測や実装方法の好みを話したら、反論せずに保留メモへ移してください。指示書には入れません。推測を伝えると、poteto-mode の調査範囲がそこに絞られるからです。

## 指示書の形

決まったことだけを書いてください。壁打ちの経過、却下した案、あなたの推奨のうち方法や原因に触れるものは書きません。項目が空のときは見出しごと省きます。

```markdown
## 目標
何が問題か、または何を望んでいるか。

## 完了チェック
合格か不合格かで判定できる条件。

## 見たい証拠
実際のコマンド出力、操作動画、保存された値、変更前後の数値など。

## 既知の事実
症状、再現手順、ログ、リンク。

## 制約
「まず再現する」「動作を変えない」「実装前に方針をレビューさせて」など。

## 決定済み（製品判断）
スコープとその外側。

## 未決（観測で決める）
プロトタイプや計測で決めるべき問い。
```

## 保存

ユーザーが指示書の内容を確定したら、保存先を決めてください。

1. `gh auth status` と `gh repo view --json nameWithOwner` が両方成功すれば、GitHub issue にします。タイトルと本文をユーザーに見せ、作成の了承を得てから `gh issue create --title <title> --body-file <file>` で作成します。本文はファイル経由で渡し、コマンドラインに直接埋め込みません。
2. どちらかが失敗したら、`docs/briefs/<YYYY-MM-DD>-<slug>.md` に保存します。commit はしません。

保留メモは issue にも docs にも書かず、最後の返信にだけ含めてください。issue のコメント欄も poteto-mode に読まれるため、そこにも書きません。

## 最後の返信

次の 3 つを返してください。

1. 保存先（issue の URL か、ファイルのパス）。
2. 新しいセッションに貼るプロンプト。issue なら `/poteto-mode read #<番号>`、ファイルなら `/poteto-mode read <パス> . 実装前に計画をレビューさせて` とします。
3. 保留メモ。「poteto-mode の進め方が自分の理解とずれたときに、必要なら伝える」と添えます。
