# 実装計画書を書く

## 概要

読者はこの計画をレビューする人と、この計画に従って TDD で実装するエンジニアの 2 者である。レビューする人は「何を決めたか」を短時間で確認したい。実装するエンジニアは十分に有能で、通常の開発コンテキストは把握している。

計画書の重心は **決めた仕様** に置く。仕様、テスト、タスクを ID で紐づけ、レビューが一方向に読み進められる構造にする。コードの書き方は書かない。DRY。YAGNI。TDD。

**保存先:** `docs/work/exec-plans/YYYYMMDD-<pr-name>.md`

議論の経緯は書かない。最初から計画したものとして書く。

## テンプレート

```markdown
# <pr-name>

## レビューポイント

この計画で判断してほしいこと。最大 3 点。各点に推奨案を添える。

## ゴール

この PR で何ができるようになるか。2〜3 文。機能スペックへの参照があれば添える。

## 確定仕様

- S-1: <前提>のとき、<結果>
- S-2: ...

### 異常系

- S-n: <異常な入力・状態>のとき、<結果>

### スコープ外

この PR でやらないこと。

## 設計判断

| 判断 | 採用 | 理由 |
| ---- | ---- | ---- |

一行で書く。経緯や却下案の詳細は ADR に譲る。

## 構成

| コンポーネント | 責務 | 公開インターフェース | 依存先 |
| -------------- | ---- | -------------------- | ------ |

## テスト設計

`test-design` Skill に従って書く。

## タスク

1. <タスク名>: S-1, S-2 を green にする
2. ...

## 未決事項とリスク
```

## 各セクションの書き方

### 確定仕様

- 外から観測できる振る舞いだけを書く。処理手順、アルゴリズム、データ構造は書かない。
- 1 項目 1 テストの粒度にする。
- 異常系とスコープ外を必ず書く。空なら「なし」と書き、検討したことを示す。
- 項目が 10 を超えたら PR の分割を提案する。

### 構成

- コンポーネントの責務、公開インターフェースの入出力、依存の向きまで書く。
- 公開インターフェースは入出力の意味が分かる程度に書く。シグネチャの完全な記述や内部ロジックは書かない。
- ファイルパスは配置先の目安として添えるにとどめ、既存コードベースの慣習に従う。
- 既存コードベースでは確立されたパターンに従う。変更対象が肥大化している場合に限り、分割を計画に含める。

### タスク

- 中規模の機能なら 4〜7 個に収める。
- 各タスクは「どの S-n を green にするか」で定義し、完了時に単独で意味をなす変更になるようにする。
- 順序は依存関係とリスクで決める。先に不確実な部分を片づける。
- red-green-refactor の各小手順は列挙しない。
- 進捗はタスク単位のコミットで追う。計画書に進捗を書き込まない。

## 書かないこと

- 会話の経緯、却下した案の詳細
- 関数の内部処理、変数名、コードスニペット
- diff を見れば分かる変更ファイルの網羅的な一覧
