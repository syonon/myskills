# TDD で実装する

## 前提

- 読む計画書は `docs/work/exec-plans/` にある今回の PR のものだけ。他の計画書や過去の Issue は読まない。
- テストの書き方は、言語別のテスト Skill があればそれに従う。
- 計画書に進捗を書き込まない。進捗はコミットで追う。計画書を編集するのは仕様の修正が合意されたときだけ。

## タスクごとのサイクル

1. **RED**: タスクに紐づくテストを、テスト設計に従って書く。実行して失敗を確認する。失敗の理由が「仕様を満たしていないから」であること。import エラーや typo による失敗は red ではない。
2. **GREEN**: テストを通す最小の実装を書く。既存のテストを壊さない。
3. **REFACTOR**: テストを green に保ったまま、重複と分かりにくさを取り除く。
4. 全テストを実行する。
5. コミットする。1 タスク 1 コミット。メッセージは日本語の Conventional Commits。

## 守ること

- テストを通すために期待値を変えない。
- 計画書にない仕様を実装しない。
- テスト設計から逸脱する場合は理由をコミットメッセージに残す。実装中に不要と分かったテストは消してよく、足りないと分かったテストは仕様に紐づく限り足してよい。

## 仕様とのずれに気づいたら

実装中に仕様の矛盾や不足に気づいたら実装を止め、ユーザーに報告する。勝手に解釈しない。計画書を更新し、合意してから再開する。

## 全タスク完了後

1. 全テストと lint を通す。
2. `code-simplify`、`codex-review` で仕上げる。
3. `docs-feature-specification` Skill で `docs/specs/` の長期仕様を更新する。計画書を削除する前に行う。
4. `writing-pr-description` Skill で PR を作る。計画書の転記と削除はそこで行う。
