# アーキテクチャデシジョンレコード（ADR）

コーディングセッション中に発生したアーキテクチャ上の意思決定を記録する。意思決定がSlackスレッド、PRコメント、あるいは誰かの記憶の中だけに残るのではなく、このスキルによってコードと一緒に保管される構造化されたADRドキュメントを生成する。

## 起動条件

- ユーザーが明示的に「この決定を記録しよう」または「ADRにして」と発言した場合
- ユーザーが重要な選択肢（フレームワーク、ライブラリ、パターン、データベース、API設計）の中から選択する場合
- ユーザーが「〜にすることにした」や「YではなくXにした理由は...」と発言した場合
- ユーザーが「なぜXを選んだのか？」と質問した場合（既存ADRを参照）
- アーキテクチャ上のトレードオフが議論される計画フェーズ

## ADRフォーマット

下記の軽量MADRフォーマットをAI支援開発向けに適用したものを使用する：

```markdown
---
status: "{proposed（提案中） | rejected（却下） | accepted（承認済み） | deprecated（非推奨） | … | superseded by ADR-0123（ADR-0123に置き換え済み）}"
date: { 最終更新日 YYYY-MM-DD }
---

# {解決した問題と採用した解決策を表す短いタイトル}

## 背景と問題の概要

{背景と問題の概要を記述します。例えば、2〜3文の自由記述や、具体的なストーリー形式で説明します。
問題を疑問文の形で表現したり、コラボレーションボードや課題管理システムへのリンクを追記しても構いません。}

## 検討した選択肢

- {選択肢1のタイトル}
- {選択肢2のタイトル}
- {選択肢3のタイトル}
- … <!-- 選択肢の数は状況に応じて変えてください -->

## 決定結果

**採用した選択肢: {選択肢1のタイトル}。**

理由: {根拠。例: 必須条件を満たす唯一の選択肢であるため | 課題 {課題名} を解決するため | … | 総合的に最も優れているため（詳細は後述）}。

<!-- この項目は任意です。不要であれば削除してください。 -->

### 影響

- 良い点: {ポジティブな影響。例: 特定の品質特性の改善など。}
- 悪い点: {ネガティブな影響。例: 特定の品質特性のトレードオフなど。}
- … <!-- 影響の数は状況に応じて変えてください -->
```

## ワークフロー

### 新規ADRの記録

意思決定の瞬間が検出された場合：

1. **初期化（初回のみ）** — `docs/adr/` が存在しない場合、ディレクトリの作成、インデックステーブルヘッダー（下記「ADRインデックスフォーマット」参照）を含む `README.md`、手動使用のための空のテンプレートの作成について、ユーザーに確認を求める。明示的な同意なしにファイルを作成しない。
2. **決定を特定する** — 行われようとしているアーキテクチャ上の核心的な選択を抽出する
3. **背景を収集する** — 何がこの問題を引き起こしたか？どのような制約があるか？
4. **代替案を文書化する** — 他にどのような選択肢が検討されたか？なぜ却下されたか？
5. **影響を記述する** — トレードオフは何か？何が容易になり、何が困難になるか？
6. **番号を付与する** — `docs/adr/` 内の既存ADRをスキャンしてインクリメントする
7. **確認して書き込む** — ADRの下書きをユーザーに提示してレビューを依頼する。明示的な承認を得てから `docs/adr/NNNN-decision-title.md` に書き込む。ユーザーが却下した場合、ファイルを書き込まずに下書きを破棄する。
8. **インデックスを更新する** — `docs/adr/README.md` に追記する

### 既存ADRの参照

ユーザーが「なぜXを選んだのか？」と質問した場合：

1. `docs/adr/` の存在を確認する — 存在しない場合、「このプロジェクトにはADRがありません。アーキテクチャ上の意思決定の記録を始めますか？」と応答する
2. 存在する場合、`docs/adr/README.md` のインデックスから関連するエントリを検索する
3. 該当するADRファイルを読み込み、「背景」と「決定」セクションを提示する
4. 一致するものがない場合、「その決定に関するADRは見つかりませんでした。今から記録しますか？」と応答する

## 意思決定の検出シグナル

会話中のこれらのパターンに注意し、アーキテクチャ上の意思決定を検出する：

**明示的なシグナル**

- 「Xにしよう」
- 「YではなくXを使うべきだ」
- 「このトレードオフは〜の理由で許容できる」
- 「これをADRとして記録して」

**暗黙的なシグナル**（ADRの記録を提案する — ユーザーの確認なしに自動作成しない）

- 2つのフレームワークやライブラリを比較して結論に至った場合
- 根拠を伴うデータベーススキーマ設計の選択を行った場合
- アーキテクチャパターン（モノリス vs マイクロサービス、REST vs GraphQL）の選択を行った場合
- 認証・認可戦略の決定を行った場合
- 代替案の評価後にデプロイインフラを選定した場合

## 良いADRの条件

### すべきこと

- **具体的にする** — 「ORMを使う」ではなく「Prisma ORMを使う」
- **理由を記録する** — 何をしたかよりも、なぜそうしたかが重要
- **却下した代替案を含める** — 将来の開発者は何が検討されたかを知る必要がある
- **影響を正直に記述する** — すべての決定にはトレードオフがある
- **簡潔にする** — ADRは2分で読めるべきである
- **現在形を使う** — 「Xを使う予定」ではなく「Xを使う」

### すべきでないこと

- 些末な決定を記録する — 変数命名やフォーマットの選択にADRは不要
- 長文を書く — 背景セクションが10行を超えるなら長すぎる
- 代替案を省略する — 「なんとなく選んだ」は有効な根拠ではない
- 後から記録する際にその旨を明記しない — 過去の決定を記録する場合は元の日付を記載する
- ADRを放置する — 置換された決定には後継ADRへの参照を記載すべきである

## ADRのライフサイクル

```
提案中 → 承認済 → [非推奨 | ADR-NNNNにより置換]
```

- **提案中**: 決定は議論中であり、まだ確定していない
- **承認済**: 決定は有効であり、遵守されている
- **非推奨**: 決定はもはや関連性がない（例：機能が削除された）
- **置換**: より新しいADRがこの決定を置き換えた（必ず後継ADRをリンクする）

## 記録すべき決定のカテゴリ

| カテゴリ                   | 例                                                                |
| -------------------------- | ----------------------------------------------------------------- |
| **技術選定**               | フレームワーク、言語、データベース、クラウドプロバイダ            |
| **アーキテクチャパターン** | モノリス vs マイクロサービス、イベント駆動、CQRS                  |
| **API設計**                | REST vs GraphQL、バージョニング戦略、認証方式                     |
| **データモデリング**       | スキーマ設計、正規化の決定、キャッシュ戦略                        |
| **インフラストラクチャ**   | デプロイモデル、CI/CDパイプライン、監視スタック                   |
| **セキュリティ**           | 認証戦略、暗号化アプローチ、シークレット管理                      |
| **テスト**                 | テストフレームワーク、カバレッジ目標、E2E vs 結合テストのバランス |
| **プロセス**               | ブランチ戦略、レビュープロセス、リリースサイクル                  |

## 他のスキルとの連携

- **プランナーエージェント**: プランナーがアーキテクチャ変更を提案した際、ADRの作成を提案する
- **コードレビューエージェント**: 対応するADRなしにアーキテクチャ変更を導入するPRにフラグを立てる
