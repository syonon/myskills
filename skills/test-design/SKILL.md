# テスト設計

テストの目的は、確定仕様が満たされていることを証明し、仕様が変わらない限り壊れないことである。実装の詳細を固定するためのものではない。

**入力:** 計画書の確定仕様と構成
**出力:** 計画書のテスト設計セクション

## 手順

1. 確定仕様の各項目について、その振る舞いを観測できる最も内側の境界を選び、テストレベルを決める。
2. 入力に範囲、区分、条件の組み合わせ、状態がある仕様には、下の技法を当てて必要なケースを洗い出す。単純な仕様には 1 ケースでよい。
3. 技法を当てる過程で仕様に書かれていない振る舞いが見つかったら、テストを勝手に作らず、計画書の未決事項に戻す。
4. テスト設計表にまとめる。

## 観点の適用

| 技法               | 使う条件                                         | 最低限のケース                                   |
| ------------------ | ------------------------------------------------ | ------------------------------------------------ |
| 同値分割           | 入力に有効・無効の区分がある                     | 各区分から 1 件                                  |
| 境界値分析         | 数値範囲、長さ、件数、日時の閾値がある           | 各境界の内側と外側 1 件ずつ                      |
| デシジョンテーブル | 複数条件の組み合わせで結果が変わる               | 結果が変わるルールごとに 1 件。全組み合わせは不要 |
| 状態遷移           | 状態を持ち、遷移で振る舞いが変わる               | 有効な遷移ごとに 1 件、代表的な無効遷移 1 件     |

## 良いテストの条件

- 確定仕様を根拠にする。根拠のないテストは書かない。
- 1 つのテストが 1 つの仕様を検証する。
- 公開インターフェースを通して振る舞いを検証する。内部の状態や処理の順序を見ない。
- 仕様を変えずに実装を書き換えても通る。
- 失敗したとき、どの仕様が満たされていないかがテスト名と失敗メッセージから分かる。
- テストダブルは自分の制御下にない外部との境界に限って使い、ダブル自体の挙動を検証しない。
- テスト名は仕様の文にケースの条件を添えたものにする。計画書を削除した後、テストが仕様の記録として残る。

## テストしないこと

- 言語、フレームワーク、外部ライブラリの振る舞い
- 仕様を持たない単純な受け渡し
- 確定仕様にない振る舞い

## テスト設計表

```markdown
| ID  | 仕様 | 観点     | 前提と入力 | 期待結果 | レベル |
| --- | ---- | -------- | ---------- | -------- | ------ |
| T-1 | S-1  | 正常系   |            |          | unit   |
| T-2 | S-1  | 境界値   |            |          | unit   |
```

観点には、正常系、異常系、または適用した技法名を書く。
