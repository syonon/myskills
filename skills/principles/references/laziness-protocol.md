# 怠惰のプロトコル

最小のコードと複雑さで、最大の成果を得る。

- **削除を優先する。** リファクタリングや改善を頼まれたら、足す前に消せるものを探す。
- **呼び出し階層を浅く保つ。** 深い呼び出しの連鎖を避ける。多くの処理を隠す充実したインターフェースは、深い連鎖には当たらない。1 つの疑問に答えるのに 3 つを超えるファイルやレイヤーを追う必要があるなら、平らにする。
- **判断を 1 か所にまとめる。** 同じ判断を複数の場所で繰り返さない。1 つの情報源に置き、結果を単純なフラグとして渡す。
- **差分を最小にする。** 問題を解決する最小の変更をする。「エレガントな」定型コードより、行数が少ないほうがよい。
- **値の受け渡しを疑う。** 新しいシグナルを型、スキーマ、パイプラインなどの層に通して渡すよう求められたら、手を止めて、もっと直接的な経路を探す。
- **小さな漏れを放置しない。** 小さな素通しの関数、内部表現の漏れ、重複した判断は、広がる前に取り除く。小さな漏れは積み重なり、恒久的な調整コストになる。

**確認:** 人間の開発者が保守にうんざりするコードなら、それは悪い解決策である。
