# 教訓を構造に埋め込む

繰り返し必要になる修正は、文章の指示ではなく仕組み（ツール、コード、メタデータ、自動化）に埋め込む。エラー、人間による修正、予想外の結果は、すべて学習の信号である。捕まえ、振り分け、ループを閉じる。

**理由:** 文章の指示は見落とされやすい。読み手が気づき、覚え、従わなければ効かない。構造的な仕組み（lint ルール、メタデータのフラグ、実行時チェック、自動化スクリプト）は、協力がなくてもルールを強制する。

**進め方:**
同じ指示を 2 回書いていると気づいたら、
1. lint ルール、メタデータのフラグ、実行時チェック、スクリプトにできるかを問う
2. できるなら埋め込み、指示は消す
3. できないなら（判断が必要なら）、指示を目立たせ、失敗例を添える

**最も強い仕組みを選ぶ。** 複数の仕組みが使えるなら、状況が許す最も強いものを選ぶ。強い順に、コンパイルできない表現不能な状態、CI を落とす lint や禁止 API、標準のヘルパー、実行時チェックである。エージェントは周りのコードがしていることを真似るので、弱い歯止めは次の手本になってしまう。

**帰結:** 修正が構造で済むなら、構造だけで直す。指示は症状である。

**フィードバックループ:**
- **すべての修正を捕まえる。** 人間が介入したときやテストが失敗したとき、一度きりかパターンかを判断する。
- **適切な層に振り分ける。** 一度きりならメモ（CLAUDE.md や memory）。繰り返す修正なら Skill か lint ルール。システム全体の問題なら原則。
- **ループを閉じる。** 記録するだけで終わらせない。今すぐ適用するか、具体的な TODO を作る。

**アンチパターン:**
- 記録せずに受け止めるだけ（「覚えておきます」は残らない）
- 記録するが振り分けない（作るべき lint ルールについてのメモは、lint ルールが実装されなければ無駄になる）
- 一般化せずに直す（1 か所を直し、繰り返すパターンを残す）
