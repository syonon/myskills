# 境界の規律

検証、型の絞り込み、エラー処理はシステムの境界に置く。内部のコードは無条件に信頼する。業務ロジックは純粋関数に置き、外側の殻は薄く機械的にする。

**理由:** 散らばった検証は、うるさく、重複し、安全だという錯覚を与える。ロジックをフレームワークとの接続部分から切り離し、フレームワークなしでテストできるようにする。

**進め方:**
- **境界では**（CLI 引数、設定ファイル、外部 API、ネットワークプロトコル）、検証し、エラーを返し、防御的に扱う。
- **システムの内部では**、型付きのデータを使い、エラーは伝播させ、再検証しない。型を信頼する。
- **境界をまたぐときは**、境界の内部表現ではなくドメインの概念を公開する。汎用の仕組みは内側に、特定用途の方針は端に置く。

**適用例:**

検証とエラー処理:
- 設定は業務ロジックの中ではなく、パース時（境界）に検証する
- 生データは境界でドメインの型にパースする
- 通信、保存、フレームワーク、ワイヤ形式の型を公開面から再エクスポートしない
- 境界で検証済みなら、呼び出しの奥で冗長な null チェックをしない

コードの構成:
- 業務ロジックはフレームワークに依存しない純粋関数に置く
- パース関数は、生のバイト列から型付きの状態への純粋な変換にする
- プロンプトの組み立ては、構造化された状態を受け取り文字列を返す
- 採点や評価は、状態から結果への純粋な変換にする

**確認:**
- 「このデータは今まさにシステムの境界を越えているか」。越えていないなら、検証は冗長である。
- 「これは殻が呼ぶだけの純粋関数にできるか」。できるなら切り出す。
