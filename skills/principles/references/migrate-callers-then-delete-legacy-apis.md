# 呼び出し元を移行してから旧 API を消す

新しい API が正しい設計だと決めたら、互換レイヤーを残さず、同じリファクタリングの段階で呼び出し元を移行し、旧 API を消す。

**ルール:**
- 内部の呼び出し元が残っているという理由だけで、旧 API の経路を残さない
- 呼び出し元を洗い出して移行し、すぐに旧 API を消す
- 一時的なアダプタは例外として期限付きで扱い、既定の構成にしない
- テストは新しい契約を検証するように更新し、リファクタリング前の実装詳細だけを守るテストは消す

**適用する条件:**
- 後方互換性に依存する外部の利用者がいない
- プロジェクトが、調整された破壊的変更を吸収できる
- 新しい API が、単純化やリファクタリングの取り組みの一部である

新旧の API を両方残すと、経路が 2 つある複雑さが生まれ、整理が遅れ、コードベースが追記しかできないもののように感じられる。
