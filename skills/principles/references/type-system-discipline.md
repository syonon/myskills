# 型システムの規律

型チェッカーは証明支援系である。ありえない状態、取り違えたプリミティブ、処理されていないバリアントを、コンパイル時に取り除くために使う。型が無視を許したケースは、コンパイラが止められたはずの実行時エラーになる。ハンドラを増やすより、エラーや特殊ケースそのものが存在しない定義を選ぶ。表現できない状態、全域関数、インターフェースの再設計（下の各パターン）がそのための道具である。

型のある言語すべてに当てはまる。言語固有の書き方は、各言語の Skill（例: `python-patterns`）に従う。

**パターン:**

- **不正な状態を表現できなくする。** バリアントは直和型で表す。TypeScript の判別共用体、Rust・Swift・Kotlin のペイロード付き enum、Scala の sealed class、Haskell・OCaml の代数的データ型などである。矛盾する組み合わせがコンパイルを通る、省略可能なフィールドの寄せ集めで状態を表さない。気づきにくいアンチパターンとして、`{ completed: boolean; completedAt?: Date }` は `completed: true; completedAt: undefined` という無意味な値を許す。真偽値は `completedAt !== null` のように 1 つの情報源から導出するか、`{ kind: 'open' } | { kind: 'done'; at: Date }` のようにバリアントを明示する。バグを前に「待て、この組み合わせは本当に起こりうるのか」と考えさせられたら、型が緩すぎる。
- **型は制限ではなく構成である。** 緩い型からチェックで値を削り出すのではなく、欲しい値から型を組み立てる。篩型（refinement type）が必要に見える不変条件も、たいていは構成を変えれば表せる。空でないリストは長さをチェックしたリストではなく、先頭要素と残りの組である。正しい時間範囲は、順序を保たなければならない 2 つのタイムスタンプではなく、開始時刻と長さの組である。特別扱いされる表現はない。ペアのリストは、そう解釈すれば偶数長のリストである。不正な値を作れない形を選び、その上に呼び出し側が必要とするインターフェースを公開する。
- **意味を持つプリミティブを区別する。** `UserId` と `OrderId` は中身は文字列でも、入れ替え可能であってはならない。Rust の newtype、Swift の opaque type、Kotlin の value class、Haskell の幽霊型、TypeScript のブランド付き交差型、Python の `NewType` などを使う。生成時に 1 回だけ検証し、以降は型を信頼する。
- **外部データはパースするまで型がない。** RPC のペイロード、JSON、IPC メッセージ、CLI 引数、設定ファイル、環境変数、データベースの行が該当する。すべての境界に、構造のない入力を型付きのモデルに変えるパース関数を置く。検証をどこに置くかは [境界の規律](boundary-discipline.md) を参照する。
- **型システムに嘘をつかない。** キャスト、安全でない型変換、コンパイラを迂回する assertion 関数は、潜在的な実行時クラッシュである。コンパイラが事実を証明できないなら、自分で証明する（検証する、絞り込む、モデルを精密にする）か、キャストが危険だと受け入れる。
- **網羅的なマッチはコンパイラに任せる。** 直和型でマッチするとき、新しいバリアントを処理せずに追加したらコンパイルが失敗するようにする。言語の慣用句を使う。TypeScript の `never` 型への束縛、Rust の注釈なしの `match`、Haskell の `-Wincomplete-patterns`、Kotlin の sealed class の網羅性チェック、Python の `assert_never` などである。
- **信頼できるスキーマから型を導出する。** Protocol Buffers、OpenAPI 仕様、GraphQL スキーマ、データベースのマイグレーション、デザインシステムのトークンファイルが形を定義しているなら、並行する型を手書きせずに導出する。[教訓を構造に埋め込む](encode-lessons-in-structure.md) を参照する。
- **部分性が現れる場所でだけ型を強める。** 実行時の assertion、null チェック、「ここには来ないはず」の throw は、型が弱すぎる場所の印である。そのチェックを型に押し上げる。そこで止める。型システムの役割は、各利用箇所が扱うべきケースを追跡することであり、データをできるだけ精密に記述することではない。全域関数を選ぶ。空リストの `sum` は 0 なので普通のリストを受け取る。空リストの `head` には答えがないので、空でないリストを要求する。

**確認:**

- 「このフィールドの組み合わせがいつ有効かを説明するコメントが書けるか」。書けるなら型が緩すぎる。直和型に分ける。
- 「関数の引数のうち 2 つが同じプリミティブ型なのに意味が違わないか」。違うなら区別する。
- 「この `any`、この `as`、この `assertNotNull` はどこから来たのか」。境界までたどり、そこで検証する。
- 「来月新しいバリアントが追加されたら、コンパイラは次のエージェントにケースを足す場所を教えるか」。教えないなら、マッチは網羅的ではない。
- 「この型は、別のファイルが持つ形を重複して書いていないか」。書いているなら導出する。
- 「この型を強めるのは、操作を全域に保つためか、単により精密にするためか」。強めなければ panic する箇所がないなら、普通の型のままにする。
