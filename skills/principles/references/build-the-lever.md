# てこを作る

自明でない作業は、手でやらず、その作業をするツールを作る。

**理由:** 利点は 2 つある。1 つ目は処理量である。codemod、生成器、スクリプトは毎回同じやり方で作業し、何度でも無料で再実行できる。2 つ目は確信である。ツールは、レビューする人が読んで再実行し、作業を確かめられる 1 つの成果物になる。手作業の変更は、もう一度やり直さないと確かめられない。決定的なスクリプトは「信じてください」を「これを実行してください」に変える。

**進め方:** 既定ではてこを作る。省略するのは、見てすぐ分かる明らかな編集が 2、3 か所だけの自明な作業のときに限る。

- 最初の 1 単位は手でやって手順を学び、それからツールを作る。その単位でツールを再実行し、手作業の結果との diff を取って正しさを示す。ツールは再実行しても安全にする。
- 編集には codemod やスクリプト、繰り返しのファイルには生成器、分析には SQLite に落として問い合わせるクエリ、検証には再実行できるチェックを使う。
- 決定的なてこは、作業の並列分担に勝る。ツールが全単位を 1 回で処理できるなら、自分で実行する。スクリプトでできることを、サブエージェントに分けて手作業させない。
- サブエージェントに作業を分けるときは、てこを全員が読む Skill として書く。手順、検証の約束、触ってはいけない範囲を 1 つの成果物にまとめる。サブエージェントの書き込み範囲の外に置き、約束をこっそり書き換えられないようにする。
- この原則を適用すると、ファイルが生まれる。原則を引用したのに diff に codemod、スクリプト、生成器、委任用の Skill がないなら、適用していない。
- 作業がセッションを越えて続くなら、てこをコミットする。

**バランス:** 基準は繰り返しかどうかではなく、自明かどうかである。1 回きりの作業でも、てこがあることで作業を確かめられるなら、てこを作る価値がある。[怠惰のプロトコル](laziness-protocol.md) に従い、作業をするか証明する最小のスクリプトを作る。フレームワークは作らない。

[教訓を構造に埋め込む](encode-lessons-in-structure.md) とは別の原則である。あちらは繰り返す指示を恒久的な歯止めにする。こちらは目の前の作業の処理量とレビューのしやすさのためのものである。検証そのものをスクリプトにすることは [動くことを証明する](prove-it-works.md) を参照する。
