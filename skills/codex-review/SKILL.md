呼び出されたら、Codex CLIを使用してコードレビューを実行してください。

レビューは **「初回レビュー → 修正 → 再レビュー」のループ** です。再レビューでは初回と同じCodexセッションを継続し、前回の指摘をCodex側のコンテキストに残したまま「解消されたか」を判定させます。

セッションの継続はあくまで**精度と速度のための最適化**です。継続できない状況になったら粘らず、新規レビューに切り替えてループを先に進めてください。

## 初回レビュー

`codex exec review` を実行し、**セッションID（thread_id）を必ず控えます**。再レビューに必要です。

```bash
codex exec review --uncommitted --json -o .tmp/codex-review-last.md > .tmp/codex-review-last.jsonl
jq -r 'select(.type=="thread.started") | .thread_id' .tmp/codex-review-last.jsonl
```

- `--json` はイベントをJSONL出力する。1行目の `thread.started` に `thread_id` が入る
- `-o` はレビュー本文（最終メッセージ）をファイルに書き出す。結果はこのファイルから読む
- 得られた `thread_id` は会話中ずっと保持する。`.tmp/codex-review-last.jsonl` にも残るため後から復元できる

### レビュー対象の指定

`[PROMPT]` は位置引数であり、`--uncommitted`、`--base`、`--commit` と**組み合わせることはできません**。

| 対象 | フラグ |
| --- | --- |
| 未コミットの変更（ステージ済み・未ステージ・未追跡） | `--uncommitted` |
| ベースブランチとの差分 | `--base main` |
| 特定のコミット | `--commit <SHA>` |
| 自由形式のレビュー指示 | `"エラーハンドリングに注目して"`（単独で使用） |

## 再レビュー（2回目以降）

`thread_id` があるなら `codex exec resume` で同一セッションを継続します。新規に `codex exec review` を実行するとCodex側のコンテキストが失われ、レビュー対象の把握を一からやり直すことになるためです。

```bash
codex exec resume "$THREAD_ID" -c sandbox_mode='"read-only"' \
  -o .tmp/codex-review-rereview.md \
  "指摘に対応しました。現在の未コミット変更を再レビューしてください。
前回の各指摘について 解消 / 部分的 / 未解消 のいずれかを判定し、
加えて今回の修正で新たに混入した問題があれば指摘してください。"
```

- 前回の指摘はCodex側に残っているため、こちらから指摘内容を再送する必要はない
- `-c sandbox_mode='"read-only"'` を必ず付ける。resumeは通常のエージェントターンとして走り、既定ではワークスペースへの**書き込みが可能**なため、レビュー用途では読み取り専用に固定する
- `codex exec resume` には `--cd/-C` が**無い**。対象リポジトリのディレクトリで実行する
- 再レビューはレビューモードではないため出力形式が固定されない。上記のように**期待する出力形式をプロンプトで明示する**
- 3回目以降も同じ `thread_id` を使い続ける

### thread_idが分からない場合

以下を**上から1回ずつ試し、成功した時点で打ち切る**。ここで代替手段を探し回らないこと。

1. 会話中に控えた `thread_id` を使う
2. 無ければ `jq -r 'select(.type=="thread.started") | .thread_id' .tmp/codex-review-last.jsonl` で復元する
3. それでも取れない、または `codex exec resume` がエラーになったら、**セッション継続を諦めて「初回レビュー」の手順を新規に実行する**。前回の指摘は自分のコンテキストに残っているので、新しいレビュー結果と突き合わせて解消状況を判断すればよい

`codex exec resume --last` や `~/.codex/sessions` の走査は使わない。誤ったセッションを掴んでも失敗が表面化せず、誤った再レビュー結果になるため。

## ワークフロー

1. **スコープを確認する**: レビュー対象が明確でない場合はユーザーに確認する — 未コミットの変更、ブランチの差分、または特定のコミット。
2. **初回レビューを実行する**: 適切なフラグで `codex exec review` を実行し、`thread_id` を控える。
3. **結果を提示する**: `-o` で出力されたレビュー本文をユーザーに共有する。重大な問題は提案事項とは別に強調する。
4. **修正を支援する**: ユーザーが対応したい指摘について、変更の実装を支援する。
5. **再レビューする**: 修正後は `codex exec resume` で同一セッションを継続し、指摘の解消状況を判定させる。継続できなければ新規レビューにフォールバックする。未解消が残る場合は4に戻る。

## 重要なガイドライン

- ユーザーが詳細を指定せずに「変更をレビューして」と言った場合は `--uncommitted` をデフォルトとする
- フィーチャーブランチの全差分をレビューする場合は `--base main` を使用する
- 「再レビュー」「もう一度見て」と言われたら、まずresumeを試す。使えなければ新規reviewでよい
- セッション継続に失敗しても立ち止まらない。フォールバックしたことを一言添えてレビューを続行する
- レビューは参考意見として扱う — すべての提案を適用する必要はない
