# 機能仕様書を作成・同期する

このスキルは、実装済みの機能について `docs/specs/` 配下の機能仕様書を作成または更新するために使う。
`docs/DESIGN.md` を肥大化させず、詳細仕様を機能単位の自然言語ドキュメントへ分離する。

このスキルは、TDDによる実装とリファクタリングが終わった後に使うことを想定している。実装・テストで確定した振る舞いを機能仕様書へ同期するためのスキルである。

## 成果物

主な成果物は次のいずれか。

- `docs/specs/` 配下に追加した機能仕様書
- `docs/specs/` 配下にある既存機能仕様書の更新
- 機能仕様書の追加・更新が不要であることの説明

## 対象にする内容

機能仕様書には、現在有効な機能仕様として長期参照できる内容だけを書く。

| 対象             | 例                                             |
| ---------------- | ---------------------------------------------- |
| 機能の概要       | その機能が何を扱うか                           |
| 対象範囲         | 対象 API、対象ユースケース、対象データ         |
| 入力             | request、header、設定値、イベント、ファイル    |
| 出力             | response、DB record、イベント、ログ、生成物    |
| 正常系の振る舞い | 保存条件、変換ルール、状態遷移                 |
| 異常系の振る舞い | エラー応答、スキップ条件、再試行、失敗時の影響 |
| データ仕様       | 保存フィールド、値の解決順、NULL 許容、形式    |
| 整合性           | 冪等性、一意制約、重複時の扱い                 |
| スコープ外       | 明示的に扱わないこと                           |

## 既存仕様との責務分離

新しい機能仕様書を書く前に、対象機能に関連する既存の正本仕様がないか確認する。
特に persistence、認証、observability、共通 error handling のような横断関心は、既存の専用仕様書を正本として優先する。

既存の正本仕様がある場合、新規仕様書には次だけを書く。

- その機能固有の振る舞い
- どの既存仕様が適用されるか
- 既存仕様に対する機能固有の前提、入口条件、対象範囲

次の内容は、新規仕様書で再定義しない。

- 保存条件
- 保存フィールド
- 共通の失敗時挙動
- 冪等性ルール
- 共通データ形式

## 書かない内容

次の内容は機能仕様書に入れない。

- PR 番号、PR の背景、実装順序、作業ログ
- 「現在のプロジェクトでは」「この時点では」など、作成時点に依存する現状説明
- brainstorm や implementation plan の検討過程
- 採用しなかった案の詳細
- 実装ファイル一覧、関連テスト一覧、テスト保証セクション
- private helper、関数分割、変数名などの内部実装詳細
- 正本性、Living Spec、更新ルールなどのドキュメント運用説明
- 将来実装するかもしれない未確定事項

重要な設計判断の履歴を残す必要がある場合は、機能仕様書ではなく ADR に分離する。

## 実行フロー

### 1. 対象機能を特定する

- ユーザー指定の機能名、変更ファイル、PR 用 spec、exec-plan を確認する。
- 指定が曖昧な場合は、実装差分とテスト差分から機能境界を推定する。
- 1 つの仕様書に複数の独立機能を詰め込まない。

### 2. 根拠を集める

次の順で確認する。

1. 実装コード
2. テストコード
3. DB schema、migration、設定ファイル
4. 既存の `docs/specs/`
5. PR 用 spec、exec-plan、brainstorm 由来の一時ドキュメント

一時ドキュメントは参考資料として扱う。
最終的な仕様は、実装とテストで成立している振る舞いを優先する。

### 3. 仕様化する内容を抽出する

抽出時は次の問いで整理する。

- 何を入力として受け取るか
- 何を出力または保存するか
- どの条件で処理するか
- どの条件で処理しないか
- 値はどの順序で解決するか
- 失敗時に利用者や呼び出し元へ何が返るか
- 失敗が他の処理へ波及するか
- 重複、再実行、部分失敗をどう扱うか
- 明示的にスコープ外にすることは何か

### 4. 配置先を決める

既存の情報設計に合わせて `docs/specs/` 配下に置く。
ディレクトリは機能領域、ファイル名は機能名を kebab-case にする。

例:

```text
docs/specs/persistence/llm-request-recording.md
docs/specs/proxy/anthropic.md
docs/specs/proxy/openai.md
docs/specs/streaming/sse-forwarding.md
```

既存仕様書がある場合は新規作成せず、既存ファイルを更新する。

### 5. 仕様書を書く

仕様書は、機能ごとに読みやすい章立てを選ぶ。
すべての章を機械的に埋める必要はない。

基本形:

```markdown
# <Feature Name> Specification

## 概要

## 対象

## 正常系の仕様

## 異常系の仕様

## データ仕様

## 冪等性と失敗時の扱い

## スコープ外
```

API や保存仕様のように条件が多い場合は、Markdown table を使う。
本文は現在形で書き、PR やフェーズの経緯に依存する表現を避ける。

### セクション選択の目安

| 機能の種類  | 使いやすい章                                     |
| ----------- | ------------------------------------------------ |
| Proxy / API | 対象 endpoint、request、response、header、error  |
| DB 保存     | 保存条件、保存フィールド、冪等性、保存しない条件 |
| Streaming   | event 形式、完了条件、中断時の扱い、除外 event   |
| Batch / Job | 入力、処理単位、再実行、失敗時の扱い             |
| Cost / 集計 | 入力データ、計算ルール、丸め、未解決時の扱い     |

## 品質チェック

編集後に次を確認する。

- 実装とテストで成立している現在仕様だけを書いているか
- PR 背景、作業順序、過去時点の現状説明が混ざっていないか
- `docs/DESIGN.md` に置くべき全体設計と重複していないか
- 仕様書単体で、入力・出力・保存条件・失敗時挙動が理解できるか
- コードを読まないと意味が分からない内部実装名に寄りすぎていないか
- 将来の数回の実装変更で腐りやすいファイル一覧やテスト一覧を書いていないか
- 既存の `docs/specs/` と矛盾していないか
