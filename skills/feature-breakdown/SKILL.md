# 機能の分解と PR 分割

やりたいことを PR 単位の作業に分解する。ここで決めるのは全体の方向と切り方だけで、各 PR の詳細仕様は決めない。詳細は PR ごとに `implementation-plans` Skill で詰める。

**保存先:** `docs/work/features/YYYYMMDD-<feature-name>.md`

## 進め方

1. コードベースを調査し、関連する既存機能、制約、確立されたパターンを把握する。調査で分かることはユーザーに聞かない。
2. `grill-me` Skill で次を確定する。
   - なぜやるのか。誰にどんな変化が見えるか
   - スコープとスコープ外
   - 全体に影響する設計判断。データモデル、外部インターフェース、既存機能との関係
   - 壊してはいけない既存の振る舞い
3. PR に分割し、順序と依存を決める。
4. 機能スペックを書く。
5. 全体に影響する判断があれば、`architecture-decision-records` Skill で ADR を残すかユーザーに確認する。

機能スペックは作業用であり、Issue への転記と削除は `writing-pr-description` Skill が最後の PR の作成前に行う。

## PR 分割の原則

- 各 PR は単独でマージでき、マージ後にテストで検証できる振る舞いを持つ。
- レイヤーではなく振る舞いで切る。「モデル層だけ」「API 層だけ」の PR は作らない。
- 振る舞いを変えない準備リファクタリングは、先行する別 PR にする。
- 不確実性が高いもの、他の PR の前提になるものを先にする。
- 1 つの PR に含まれる確定仕様が 10 を超えそうなら分割する。

## 機能スペックのテンプレート

```markdown
# <feature-name>

## 目的

なぜやるのか。2〜3 文。

## ユーザーから見える変化

完成したとき、誰に何が見えるか。

## スコープ外

やらないことを明示する。

## 全体の設計判断

PR をまたいで効く判断だけ。選んだ案と一行の理由。経緯は ADR に譲る。

## 壊してはいけない振る舞い

既存の仕様のうち、この変更で影響を受けうるもの。

## PR 分割

| # | PR | 目的 | 含む振る舞い | 依存 | マージ後に検証できること |
| - | -- | ---- | ------------ | ---- | ------------------------ |

## 未決事項

PR の計画時に決めればよいこと。
```

## 書かないこと

- ファイル構成や関数名などの実装詳細
- PR ごとの詳細仕様やテスト設計
- 議論の経緯。最初から計画したものとして書く
