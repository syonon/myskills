## PR description の書き方

- 「何を変更したか」と「レビュアーが見るべき点」に絞る。実装の手順を逐一説明しない
- 詳細設計は Issue のコメントに転記している。リンクを貼り、設計の詳細はそちらに譲る。PR 本文に重複させない
- 実装ファイルの一覧など、diff を見れば分かる情報は書かない

## PR 作成前の後始末

`docs/work/` 配下の計画書と機能スペックは作業用であり、PR に含めない。PR を作る前に次を行う。

1. 計画書の最終版を、対応する Issue のコメントに転記する。Issue がなければユーザーに転記先を確認する。
2. 計画書を削除する。
3. その機能の最後の PR であれば、`docs/work/features/` の機能スペックも同様に転記して削除する。

PR 本文の設計へのリンクは、転記先の Issue コメントを指す。
