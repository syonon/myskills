# PR 単位の実装計画

`grill-me` Skill で 1 つの PR の仕様と設計を詰め、合意した内容を `writing-plans` Skill で計画書にする。テスト設計は `test-design` Skill で行う。ここでは実装に移らない。

**入力:** `docs/work/features/` の機能スペックにある該当 PR の行、またはユーザーが指定した Issue
**出力:** `docs/work/exec-plans/YYYYMMDD-<pr-name>.md`

機能スペックがなく 1 つの PR で収まる変更なら、`feature-breakdown` Skill を経ずにここから始めてよい。

## 手順

1. 入力を読み、コードベースを調査する。調査で分かることはユーザーに聞かない。
2. `grill-me` Skill で詰める。対象はこの PR のスコープだけに絞る。機能全体の判断は機能スペックに従い、再議論しない。
3. `writing-plans` Skill で計画書を書く。テスト設計セクションは `test-design` Skill に従って書く。
4. テスト設計で仕様の穴や構成の不足が見つかったら、確定仕様や構成に戻って直す。
5. 計画書のレビューポイントを提示し、ユーザーのレビューを受ける。
6. 合意後、重要な意思決定やトレードオフがあれば `architecture-decision-records` Skill で ADR を残すか確認する。

計画書は作業用であり、Issue への転記と削除は `writing-pr-description` Skill が PR の作成前に行う。

## 小さな変更の場合

確定仕様が 3 個以下なら、計画書はレビューポイント、確定仕様、テスト設計、タスクだけの最小形にする。設計判断と構成は、書くべきことがあるときだけ書く。

## 詰める内容

- なぜこの変更が必要なのか
- 何を満たせば完成なのか。観測可能な振る舞いとして言えるか
- ドメイン上、壊してはいけない制約は何か
- コンポーネント間の責務と、その間のインターフェースをどう定めるか
- 各振る舞いをどの境界で検証するか

設計判断と構成を詰めるときは `principles` Skill の索引を参照する。特に foundational-thinking、model-the-domain、boundary-discipline、subtract-before-you-add、redesign-from-first-principles が当てはまることが多い。

## 質問の仕方

- 選択肢を提示するときは概要だけでなくトレードオフを説明し、推奨案を示す。
- 仕様の質問は「どう実装するか」ではなく「どう振る舞うべきか」の形で行う。
- 異常系、境界、スコープ外を意識して質問する。ここで曖昧なまま残すと、テスト設計で仕様の穴として戻ってくる。

## 確定仕様の条件

計画書の確定仕様は次を満たす。満たさない項目は仕様ではなく未決事項に置く。

- 外から観測できる振る舞いである。内部の処理手順ではない
- 1 項目が 1 つのテストで検証できる粒度である
- 「〜のとき、〜する」の形で、前提と結果が読み取れる
